    设计是怎么一步步定下来的 / How the design was decided

    1. 先定 LLM 放在哪里：只做入口翻译，不算几何。（第 2 步）Where the LLM goes: input translation only, no geometry. (Step 2)
    2. 再定 LLM 输出什么：SLP 关系等级，不是数字。（第 3 步）What it outputs: SLP closeness grades, not numbers. (Step 3)
    3. 然后逐个节点补上"怎么保证可靠"：①②③⑤。（第 4–7 步）Then make each node reliable: ① ② ③ ⑤. (Steps 4–7)
    4. 把等级翻译成求解器的目标和约束：⑥。（第 8 步）Translate grades into the solver's objective and constraints: ⑥. (Step 8)
    5. 最后定怎么证明它有用：⑪ 和实验设计。（第 10–11 步）Finally, how to prove it works: ⑪ and the experiment design. (Steps 10–11)

    Step 2 · Decision 1

    LLM 放在哪里：只做入口翻译

    Where the LLM goes: translation at the input only.

    有两种做法：

    There are two options:
    做法 (a) LLM 直接出布局做法 (b) LLM 翻译需求，求解器算几何
    LLM 输出每个区域的坐标和尺寸关系等级 + 规则（结构化）
    面积、不重叠靠 LLM 自己算，可能出错求解器保证，检查器复核
    能不能复核只能看结果每一对关系都有理由，可逐条查
    (a) the LLM outputs coordinates and sizes itself. (b) the LLM translates requirements; the solver computes geometry. In (b), areas and non-overlap are guaranteed by the solver, and every relation has a reason we can check.
    为什么选 (b) / WHY (b)

    1. 文献证据：Disselkamp 等（2024, NordDesign）测了 ChatGPT 在工厂规划中的 42 个用例：信息检索和量纲计算强，画布局弱。（见项目文档 02 号综述）

    Evidence: Disselkamp et al. (2024, NordDesign) tested ChatGPT on 42 factory-planning tasks. It was good at finding information and unit calculations, weak at drawing layouts.

    2. 我们已经有很强的求解器：实验一里，它在 O7、vC10a 上达到已证明的最优，在 AB20、SC30、Du62 上刷新已知最好解。没有理由让 LLM 重做几何。

    We already have a strong solver: in Experiment 1 it reached the proven optimum on O7 and vC10a and set new best results on AB20, SC30, Du62. No reason to let an LLM redo the geometry.

    3. 你定的定位：LLM 替代的是"人工理解需求"这一步。

    Your own framing: the LLM replaces the human step of understanding requirements.

    那 LLM 到底要交给求解器什么？

    So what exactly must the LLM hand to the solver?

    看求解器读的算例文件（GitHub Wsamme/FLP 的 instances/uaflp/*.json）：

    Look at the instance file the solver reads (instances/uaflp/*.json in GitHub Wsamme/FLP): 
    { "name": "O7", "n": 7, "W": 8.54, "H": 13.0,
  "areas":   [16, 16, 16, 36, 9, 9, 9],        ← 面积表直接有
  "weights": [[1, 4, 5.0], [1, 7, 1.0], ...],   ← 需要有人"判断"出来
  "shape":   {"type": "Rmax", "value": 4} }

    面积、厂房尺寸都是现成的数字。唯一需要"判断"的是 weights：哪两个区域该靠近、有多重要。这就是 LLM 的工作。

    Areas and floor size are already numbers. The only thing that needs judgement is weights: which two areas should be close, and how much it matters. That is the LLM's job.
    Step 3 · Decision 2

    LLM 输出什么：SLP 关系等级

    What the LLM outputs: SLP closeness grades.

    SLP（Systematic Layout Planning，系统布置设计，Muther 提出）的人工流程是：

    The manual SLP (Systematic Layout Planning, by Muther) process is:
    物流分析（从至表）+ 非物流关系 → 综合关系表（A/E/I/O/U/X） → 布置方案 ↑ 设计师凭经验判断的这一步，由 Agent 替代
    Flow analysis + non-flow relations → relation chart (A/E/I/O/U/X) → layout. The agent replaces the middle step, which a designer does by judgement.
    等级中文含义英文（Muther SLP）教材分值编译后的权重
    A绝对必要靠近Absolutely necessary44
    E特别重要Especially important33
    I重要Important22
    O一般Ordinary closeness11
    U不重要Unimportant00
    X不希望靠近Not desirable−1硬约束（第 8 步）
    为什么输出等级，不输出数字 / WHY GRADES

    1. 文字说明里只有定性信息（"原材料先送机加工"），没有流量数字。让 LLM 写数字就是让它编数字。

    Text only gives qualitative facts. Asking the LLM for numbers means asking it to invent them.

    2. 关系表是设计师本来就会看、会审的东西。Agent 的输出能直接拿给专家检查。

    Designers already read and review relation charts, so the agent's output can be checked by an expert directly.

    3. 经典算法 CORELAP（1967）、ALDEP（1967）的输入本来就是关系表，不是流量。（见项目文档 10 号）

    Classic methods CORELAP and ALDEP (1967) take a relation chart as input, not flows.

    4. 有现成的标准答案可以评估（第 1 步的 gold 表）。

    There is a ready answer key to score against (the gold chart from Step 1).
    Step 4 · Node ①

    ① 数值隔离：数字不进提示词

    ① Number isolation: no numbers in the prompt.

    来源 OptiMUS（ICML 2024）

    进提示词（LLM 能看到）不进提示词（直接给编译 ⑥）
    区域编号和名称
    区域功能的文字描述
    工艺流程的文字描述
    产品是什么    		 面积、长宽（如 72×36）
    物流强度数字（如 1–4: 0.3）
    任何 A/E/I/O/U/X 字母（这两个算例的）
    In the prompt: unit IDs and names, what each unit does, the process in words, the product. Not in the prompt: areas and sizes, flow numbers, any grade letters for these cases.
    为什么 / WHY

    1. 面积不需要"理解"。让数字经过 LLM 抄一遍，只会多出抄错的机会。OptiMUS 也是把数值数据和给模型看的文字分开。

    Areas need no understanding. Passing numbers through the LLM only adds chances to copy them wrong. OptiMUS also keeps numeric data apart from the text the model sees.

    2. 物流强度和关系等级高度相关（流量大 → 等级高）。给了数字等于泄题，测不出 LLM 真正的理解能力。

    Flow numbers are strongly tied to the grades (big flow → high grade). Giving them away leaks the answer.

    实际发给模型的内容（节选）真实提示词

    What the model actually receives (excerpt, real prompt): 
    # 工厂说明
……

1. 原材料库向机加工车间、热处理车间、焊接车间和工具车间供应原材料。
2. 机加工车间加工出的零件，一部分送热处理车间，一部分送变速器车间，一部分直接送总装车间。
……
# 作业单位清单（共 14 个）
- [1] 原材料库
- [2] 油料库
……
请给出全部 91 对的等级。

    怎么保证真的没泄题

    How we make sure nothing leaks:
    • 运行前自动检查 brief：不能有小数（流量）、不能有单独的等级字母、不能有"必须相邻""物流强度"等词。Before each run, the brief is checked automatically: no decimals, no single grade letters, no phrases like "must be adjacent".
    • 测试里检查提示词不含 "72×36" 这类尺寸、不含面积数。A test checks that the prompt has no sizes like "72×36" and no area values.
    • 最后一关是人：两份 brief 要你审过才跑。The last check is human: you approve both briefs before any run.

    ② 关系整理 Agent：每对一行，带理由

    ② Relation agent: one line per pair, with a reason.

    SLP 等级 · Muther 每对一行 · Holodeck（CVPR 2024） 一个 Agent 只做一件事 · Co-Layout（AAAI 2026）

    输出格式

    {"pairs": [
  {"i": 1, "name_i": "原材料库", "j": 4, "name_j": "机加工车间",
   "grade": "E", "reason": "原材料直接供给机加工", "confidence": 4},
  …  共 91 条，只列 i < j

    每个字段为什么在这里 / WHY EACH FIELD

    只做关系，不管几何：一个 Agent 只做一件事，任务越窄越不容易出错，出错也好定位。

    Relations only, no geometry: one agent, one job. A narrow task fails less and is easier to debug.

    91 对全部写出，包括 U：如果允许跳过，就分不清"模型认为是 U"还是"模型漏了"。全部写出，漏了就能被 ⑤ 抓到。

    All 91 pairs, including U: if skipping were allowed, we could not tell "the model thinks U" from "the model forgot". Listing all lets ⑤ catch omissions.

    名称和编号都写：两个互相印证。编号写错时，可以用名称发现。

    Both name and ID: they cross-check each other, so a wrong ID can be caught by the name.

    reason（理由）：错了能看出为什么错，这是第 10 步错误分析的材料。

    reason: when it is wrong, we can see why. This feeds the error analysis in Step 10.

    confidence（1–5）：给 ③ 自检用，低分的再问一次。

    confidence (1–5): used by ③. Low-confidence pairs are asked again.

    Step 6 · Node ③

    ③ 置信度自检：低分的对单独再问一次

    ③ Confidence self-check: ask again, one pair at a time, when confidence is low.

    来源 OptiMUS 逐条自检

    规则：confidence ≤ 3 → 只给这一对的两个单位 + brief，重新判断（每对一次调用） 开关：config 里 self_check = true / false，两种都跑
    Rule: if confidence ≤ 3, ask again with only this pair and the brief (one call per pair). Switch: self_check = true / false; we run both.

    例子：4–5 的 confidence = 3，触发自检 演示

    Example: pair 4–5 has confidence 3, so it is checked again (demo). 
    发给模型：
  需要复核的一对：[4] 机加工车间 与 [5] 热处理车间
  你之前的判断：等级 E，理由「机加工零件送热处理」，置信度 3。
  请独立重新判断这一对，确认或修改。

假想回复：
  {"i": 4, "j": 5, "grade": "A", "reason": "加工后的零件直接进热处理，工序紧密衔接", "confidence": 4}

    结果：4–5 从 E 改成 A。其他 5 对 confidence ≥ 4，不动。

    Result: 4–5 changes from E to A. The other 5 pairs have confidence ≥ 4 and stay.
    为什么要做成开关 / WHY A SWITCH

    1. 一次问 91 对时，模型注意力分散；单独问一对，上下文更集中。这是自检可能有用的原因。

    With 91 pairs at once, attention is spread. One pair alone gives a focused context. That is why it might help.

    2. 但自检也可能把对的改错。OptiMUS 没有单独测过这一步的效果，所以我们不假设它有用，而是开/关各跑 5 次，用数字说话。

    But it can also change right answers into wrong ones. OptiMUS did not test this step alone, so we do not assume it helps. We run it on and off, 5 times each, and let the numbers decide.

    3. 代价：每个低分对多一次调用，token 和时间都记在 meta.json 里。

    Cost: one extra call per low-confidence pair. Tokens and time are logged in meta.json.

    如果复核的回复连续 2 次解析不了，就保留原判断，并记为 recheck_failed。

    If the recheck reply cannot be parsed twice in a row, we keep the original and log recheck_failed.

    名称纠错 · Holodeck 解析失败重试 · Co-Layout 报错回传 · OptiMUS

    检查清单（每条都有测试）

    Checklist (each one has a test):
    检查不通过时
    JSON 能解析报错回传
    编号在区域表里报错回传
    名称写错按编辑距离对到最近的合法名称，记录这次纠正

    编辑距离怎么算

    How edit distance works:

    编辑距离（Levenshtein distance）= 把一个字符串改成另一个，最少要几次"插入 / 删除 / 替换一个字"。

    Edit distance = the fewest single-character inserts, deletes, or swaps to turn one string into another.
    "油料仓库" → 删去"仓" → "油料库" 距离 = 1 "热处里车间" → "里"换成"理" → "热处理车间" 距离 = 1 "油料仓库" vs "原材料库"：至少要改 2 个字 距离 ≥ 2 → 选距离最小的"油料库"

    回传循环

    The feedback loop: 
    第 0 次：模型输出 → 校验
  不通过 → 把错误原文发回："缺少 1 对: 2-3"
第 1 次：模型重写完整 JSON → 校验
  不通过 → 再发回
第 2 次：模型重写 → 校验
  还不通过 → 这次运行记为 FAILED
    为什么失败不能补 U / WHY NEVER FILL WITH U

    fork14 里 46/91 = 50.5% 的对本来就是 U。如果模型漏了 20 对、我们悄悄补 U，平均能白拿 20 × 0.505 ≈ 10 对"正确"。这会让分数虚高，所以宁可记失败，并在结果表里报失败次数。

    In fork14, 50.5% of pairs are U. If 20 pairs were missing and we quietly filled them with U, about 20 × 0.505 ≈ 10 would be "correct" for free. That inflates the score, so we record a failure and report the failure count.

    1 2 4 5 W = 1 [ 0 0 3 3 ] 2 [ 0 0 0 0 ] ← 2–5 是 X：权重记 0，另写成约束 4 [ 3 0 0 4 ] 5 [ 3 0 4 0 ]

    写进算例文件（格式和 Wsamme/FLP 的算例一致，多一个 min_separation 键）：

    Written into the instance file (same format as Wsamme/FLP, plus one extra key min_separation): 
    "areas":          [2592, 1296, 2592, 2700],      ← 直接来自面积表，不经过 LLM
"weights":        [[1,4,3], [1,5,3], [4,5,4]],
"min_separation": [[2,5,D]]                       ← D 待你定

    目标函数，代入一项

    The objective, with one term worked out.
    min Σ(i<j) w_ij × ( |cx_i − cx_j| + |cy_i − cy_j| ) c = 矩形中心
    Minimise the sum over pairs of weight × rectilinear distance between rectangle centres.

    假设机加工车间（72×36）放在左下角 (0, 0)，热处理车间（90×30）紧贴在它右边 (72, 0)：

    Say the machining shop (72×36) sits at (0, 0) and the heat-treatment shop (90×30) sits right next to it at (72, 0):
    中心 c₄ = (0 + 72/2, 0 + 36/2) = (36, 18) 中心 c₅ = (72 + 90/2, 0 + 30/2) = (117, 15) 距离 d₄₅ = |36 − 117| + |18 − 15| = 81 + 3 = 84 这一项 = w₄₅ × d₄₅ = 4 × 84 = 336

    X 为什么写成硬约束，不写成 −1

    Why X is a hard constraint, not a weight of −1.

    如果 X 记 −1 放进目标函数，意思是"两者每远 1 米，成本减 1"。它只是一个很弱的偏好，会被别的关系压过：

    If X were −1 in the objective, it would mean "each metre apart lowers the cost by 1". That is a weak preference, and other relations can outweigh it:
    油料库(2) 与 油漆车间(10) 是 E（每米 3），与 热处理车间(5) 是 X（每米 −1）。 若把油料库同时向两者靠近 10 m： 成本变化 = −3 × 10（E 变近，省）+ 1 × 10（X 变近，罚）= −30 + 10 = −20 < 0 → 求解器会接受：易燃的油料库被拉到高温炉旁边。
    Oil store (2) is E with the paint shop (10) and X with heat treatment (5). Moving the oil store 10 m closer to both changes the cost by −30 + 10 = −20. The solver accepts it, and the flammable store ends up next to the furnace.

    写成硬约束后，不管省多少成本，都不允许靠得比 D 更近。两个矩形在 x 方向或 y 方向至少隔开 D：

    As a hard constraint, it is never allowed, no matter how much cost it saves. The two rectangles must be at least D apart in x or in y:
    |cx_i − cx_j| ≥ (w_i + w_j)/2 + D 或 |cy_i − cy_j| ≥ (h_i + h_j)/2 + D

    老方法 ALDEP 用 X = −1024 这样的大负数，让它"实际上不可违反"（经蔡临宁 p.105 转引，见项目文档 10 号）；我们直接写成真正的约束。

    The old ALDEP method used X = −1024 so it was "almost never" broken. We write a real constraint instead.

    X = −1 只在第 1 步核对教材行合计时用，不进目标函数。

    X = −1 is used only to check the book's row sums in Step 1. It is not in the objective.

    Relax only E, I, O. Keep A, X, and hard rules, because A and X are the strongest statements in the chart. Relaxing them changes the design intent.

    Example: 6 pairs, before and after self-check (demo).
    对gold（书）自检前自检后错误类型

    1. 完全一致率

    等级完全相同的对数 / 总对数 自检前 = 4/6 = 0.667 自检后 = 5/6 = 0.833

    2. 相差一级以内

    顺序 A > E > I > O > U；X 必须完全一致。

    Order A > E > I > O > U. X must match exactly.
    1–2：I → U 隔了 O，差 2 级 ✗ 4–5（自检前）：A → E 差 1 级 ✓ 自检前 = 5/6 = 0.833 自检后 = 5/6 = 0.833

    3. 非 U 召回率和精确率

    Recall and precision on non-U pairs.
    gold 里非 U 的对：1–2, 1–4, 1–5, 2–5, 4–5 共 5 对 预测里非 U 的对：1–4, 1–5, 2–5, 4–5 共 4 对，全在上面 召回率 = 4 / 5 = 0.80 精确率 = 4 / 4 = 1.00

    这一项专门防"全判 U 也得高分"：全判 U 时召回率 = 0。

    This stops "all U" from looking good: all U gives recall = 0.

    4. X 召回率

    gold 里的 X：2–5（1 对），预测也是 X → 1/1 = 1.00

    安全隔离漏判最危险，所以单独报。fork14 里有 7 对 X，pump14 里有 2 对。

    Missing a safety separation is the most dangerous error, so it is reported alone. fork14 has 7 X pairs, pump14 has 2.

    5. Cohen's kappa（κ，扣除"碰巧猜对"后的一致程度）

    Cohen's kappa: agreement after removing agreement by chance.
    κ = (p_o − p_e) / (1 − p_e) p_o = 实际一致率 p_e = 按两边各等级比例，随机碰对的概率 = Σ_k (gold 中 k 的个数 × 预测中 k 的个数) / N²

    自检后的混淆矩阵（行 = gold，列 = 预测，N = 6）：

    Confusion matrix after self-check (rows = gold, columns = predicted, N = 6):
    gold ＼ 预测AEIOUX行合计
    A1000001
    E0200002
    I0000101
    O0000000
    U0000101
    X0000011
    列合计1200216
    p_o = 5/6 = 0.8333 p_e = (A 1×1 + E 2×2 + I 1×0 + O 0×0 + U 1×2 + X 1×1) / 36 = (1 + 4 + 0 + 0 + 2 + 1) / 36 = 8/36 = 0.2222 κ = (0.8333 − 0.2222) / (1 − 0.2222) = 0.6111 / 0.7778 = 0.786 自检前：p_o = 4/6 = 0.6667，预测列合计 A0 E3 I0 O0 U2 X1 p_e = (1×0 + 2×3 + 1×0 + 0 + 1×2 + 1×1) / 36 = 9/36 = 0.25 κ = (0.6667 − 0.25) / 0.75 = 0.556

    线性加权 κ：把等级按 A, E, I, O, U, X 排成 0–5，错得越远罚得越多，罚分 = |行号 − 列号| / 5。（X 排在 U 后面是我们的口径，按教材分值顺序 A4 … X−1。）

    Linear-weighted kappa: grades in order A, E, I, O, U, X get positions 0–5. The penalty is |row − col| / 5, so bigger misses cost more. (Putting X after U is our choice, following the book's score order.)
    κ_w = 1 − (实际罚分 / 随机罚分) 实际罚分 = 只有 1–2：I(2) → U(4)，罚 |2 − 4| / 5 = 0.4，占 1/6 → 0.4 / 6 = 0.0667 随机罚分 = Σ 罚分 × 行合计 × 列合计 / 36，按 gold 行 A, E, I, U, X 分别为 3.0 + 4.4 + 2.2 + 2.2 + 3.0 = 14.8 → 14.8 / 36 = 0.4111 κ_w = 1 − 0.0667 / 0.4111 = 0.838（自检前 0.743）

    为什么一定要有"全 U 基线"

    Why we need the "all U" baseline.

    在完整的 fork14 上，所有 91 对都猜 U（真实数字，不是演示）：

    On full fork14, guessing U for all 91 pairs (real numbers, not a demo):
    完全一致率 = 46/91 = 0.505 p_o = 46/91；预测全是 U，所以 p_e = (46 × 91) / 91² = 46/91 κ = (46/91 − 46/91) / (1 − 46/91) = 0 pump14：完全一致率 = 66/90 = 0.733，κ = 0

    所以只看一致率会被骗：pump14 什么都不懂也有 73.3%。Agent 必须在 κ 和非 U 召回率上明显高于 0 才算有用。

    So agreement alone can mislead: pump14 gives 73.3% with no understanding at all. The agent must clearly beat 0 on kappa and non-U recall.

    为什么重复 5 次、温度怎么定

    同一个提示词，模型每次的回答可能不一样。重复 5 次报均值 ± 标准差，看随机性有多大。

    The same prompt can give different answers each time. 5 runs give mean ± standard deviation to show how much it varies.

    原计划温度 0，但新版 Claude 模型（如 Sonnet 5.5）传非默认 temperature 会直接报 400 错误（官方迁移指南，2026-10-21 查）。所以用默认采样，随机性靠重复次数来量。

    We planned temperature 0, but newer Claude models (e.g. Sonnet 5.5) return a 400 error for non-default temperature (official migration guide, checked 2026-10-21). So we use default sampling and measure randomness with repeats.
